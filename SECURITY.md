# Security policy

## Reporting a vulnerability

**Use [private vulnerability reporting](https://github.com/patrickiel/plectrify/security/advisories/new)**
— the *Report a vulnerability* button on the Security tab. It opens a private
advisory only you and the maintainer can read, which is the point: a public
issue describing a way to get code onto someone's machine is a disclosure, not
a report.

Please do not open a public issue, and do not post it in Discord.

Plectrify is a small unfunded project with one maintainer, so there is no bounty
and no guaranteed response time. What is promised is that a report is read,
answered, and credited in the advisory unless you ask otherwise.

Useful in a report: the Plectrify version and OS, what an attacker would have to
control to pull it off, and what they get if they do.

## Supported versions

Only the most recent release. Plectrify is pre-1.0 and there are no maintenance
branches — a fix ships in the next version, not as a patch to an older one.

## What is worth reporting

The parts of Plectrify that decide whether native code or foreign data reaches a
user's machine, roughly in order of how much a flaw there would cost:

- **The plugin catalogue trust root.** The manifest is signed and its SHA-256
  pins are what authorise a DLL or dylib to be written into the VST3 load path
  and executed in this process (`Source/plugins/Catalogue.cpp`,
  `CatalogueInstaller.cpp`). Anything that installs a payload whose hash was not
  verified, gets an unsigned or wrong-key manifest accepted, or moves a
  `kind: "content"` payload into the load path, is the highest-severity class of
  bug in this repository.
- **Archive extraction.** A path-traversal entry escaping `installDir`, or a
  symlink used to write outside it (`isSafeArchiveEntryName`).
- **The web page's file sandbox.** The UI runs in an embedded web view and may
  read and write only under the per-user data root; the machine-wide content
  root is read-only to it, and `tone3000/` is denied outright because it holds a
  bearer token (`MainComponent::resolveAppFile` / `resolveSharedFile`). A path
  that escapes either boundary is a vulnerability.
- **TONE3000 credentials.** The OAuth token lives natively and must never reach
  the page, a log, a crash report, or a URL that leaves the machine.
- **The installer and the release pipeline**, including anything that would let
  a downloaded update be substituted for another binary.

## What is not a vulnerability

- **A malicious VST3 doing damage.** Plectrify is a plugin host: it loads and runs
  third-party native code that the user chose to install, in-process, with the
  user's full privileges. That is the entire product, and no host can sandbox it
  away. On macOS this requires the
  `com.apple.security.cs.disable-library-validation` entitlement, which is
  deliberate and documented in `AGENTS.md`. A plugin misbehaving is a report for
  its author.
- **Plugin scanning crashing on a broken plugin.** That is what the blacklist is
  for.
- **Anything requiring an attacker to already have write access** to the user's
  account, the VST3 folders, or `%PROGRAMDATA%`/`/Users/Shared`. Those paths are
  writable by every local account by design, so that installing a plugin needs
  no elevation; a local attacker who can write there can equally replace any
  other plugin on the machine.
- **Reports generated by a scanner against dependencies with no reachable call
  path.** Say how it is reached.
